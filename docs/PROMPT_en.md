# GUIDE - AI PROMPT MASTER

***version 1.0.0***  

*(Optimized for advanced reasoning models: OpenAI o1/o3/GPT-4o, Anthropic Claude 3.5/3.7 Sonnet, Copilot Think Deeper, DeepSeek R1)*

This guide defines communication protocols between the user and the Large Language Model for ingestion, in-memory decompression, and analysis of the compressed context generated by **chompress**.

---

## Index of Operational Workflows
- **FLOW 0: Direct Ingestion with Prompt Envelope (P4.3 - Recommended Single-Step)**
  *Suitable for:* Single files, Unix pipes, and contexts that fit within the context window without on-disk fragmentation.
- **FLOW 1: Multi-Turn Controlled Workflow (Without Chunking)**
  *Suitable for:* Multi-file repositories or sessions where one wishes to verify reconstruction prior to proceeding with refactoring or analysis.
- **FLOW 2: Workflow for Large Files (With Atomic Chunking)**
  *Suitable for:* Huge files (over 50,000-100,000 characters) partitioned into slices with `sha256_full` integrity verification.

# FLOW 1: Multi-Turn Controlled Workflow (Without Chunking)
*(Pipeline: manifest -> protocol and vocabulary -> compressed files -> exact reconstruction -> analysis)*

To be used when managing full repositories and wanting to validate the model's decompression step by step before requesting code modifications.

---

### Stage 1.1: Session Opening and Execution Constraints
*(Prevents the model from anticipating actions or inventing missing parts)*

```text
I am about to provide you in a controlled sequence:
1) The optional manifest of the project structure (manifest.json)
2) The protocol and mapping vocabulary of placeholders (protocol_header.txt and mapping_subset.txt or mapping_subset.json)
3) One or more compressed files containing the placeholders

Your operational task will be:
- Register the path structure and token alphabet.
- Treat the mapping as an exact deterministic dictionary: token -> original content.
- Await my instructions before applying substitutions.
- Reconstruct the files rigorously, character by character, without inventions, style corrections, or spacing reformatting.
- Proceed with analysis or modifications only after confirming that reconstruction has taken place.

Binding rules:
- Do NOT begin reconstruction until the explicit command: "Proceed with reconstruction".
- Confirm receipt of each element before moving to the next stage.

Confirm that you have understood and declare when you are ready to receive the manifest or the dictionary.
```

```text
It contains:
- paths: ordered list of relative file paths
- files: file index, target SHA256 hash, and list of placeholders present
- ph: analytical index of placeholders
- v: schema version

Instructions:
- Do not apply any transformation.
- Do not reconstruct anything.
- Confirm only correct receipt by stating the total number of files indexed in the manifest.

(Paste here the content of manifest.json)
```

### Stage 1.3: Insertion of Protocol and Mapping Dictionary
*(Supports both zero-key Positional Mapping and legacy JSON format)*

```text
This is the placeholder mapping dictionary generated by chompress.

If the header starts with [MAP:INDEXED...], interpret it as ordinal positional mapping:
- The header indicates the token generation rule (e.g. contiguous CJK characters cjk_start=19968 count=N, numeric prefixes prefix='^', or multiple ranges cjk_ranges).
- Entries in the payload are separated by the sentinel marker (e.g. '§').
- Each entry corresponds exactly to the n-th token generated by the protocol sequence.

If the header is [MAP:JSON], use it as a standard JSON dictionary {token: content}.

Instructions:
- Register the exact correspondence token -> content.
- Do NOT apply substitutions to the code yet.
- Confirm receipt by summarizing how many unique tokens are registered and the alphabet family (e.g. atomic CJK, prefix '^', quotes, or JSON).

(Paste here protocol_header.txt followed by mapping_subset.txt, or mapping_subset.json)
```

---

### Stage 1.4: Insertion of Compressed Files
```text
Below I send you one or more compressed files containing the registered placeholders.

Instructions:
- Register the text of each file, associating it with its respective path.
- Do NOT apply the dictionary yet.
- Confirm receipt by listing the files received and the approximate number of characters for each.

(Paste here the compressed files preceded by their relative path, e.g.: --- FILE: src/main.py ---)
```

---

### Stage 1.5: Execution of Exact Reconstruction
```text
Proceed with reconstruction.

Apply inverse substitutions to each compressed file, replacing each placeholder with its respective original vocabulary content.

Strict decoding rules:
1. No invention or inference of code not present.
2. No automatic correction of syntax, pre-existing bugs, or variable names.
3. Prefix resolution in descending length order: longer tokens take precedence to prevent prefix collisions (e.g. ^10 must not be confused with ^1 followed by 0).
4. No alteration of indentation or lines. Exact character-by-character reconstruction.
5. If a token encountered in the text does not exist in the vocabulary, abort immediately and expose the missing token.
6. If manifest.json was provided, verify correspondence with the sha hash indicated for the file.

Return the final status: "RECONSTRUCTION COMPLETED SUCCESSFULLY" and display the reconstructed code (or await the next request).
```

---

### Stage 1.6: Analysis, Refactoring, or Modifications
```text
Now that the context is fully decoded and aligned in memory, execute the following request:

(Insert the objective here, e.g.:

- Strictly maintain the original architecture.
```

# FLOW 2: Workflow for Large Files (With Atomic Chunking)
*(Pipeline: chunks/manifest.json -> mapping -> chunk fragments -> reassembly -> sha256_full verification -> decoding -> analysis)*

To be used when source files exceed prompt size or session output limits and have been partitioned via `--chunk-output`.

---

### Stage 2.1: Chunking Session Opening
```text
I am about to provide you with a large file partitioned into ordered fragments (chunks) via chompress.

You will receive in sequence:
1) The descriptor file: chunks/manifest.json
2) The token dictionary: protocol_header.txt + mapping_subset.txt (or mapping_subset.json)
3) The individual sequential chunk files (0001.txt, 0002.txt, ...)

Your task will be:
- Register each chunk without taking premature actions.
- Reassemble the text by concatenating the chunks in the exact sequential order indicated in the manifest.
- Verify the integrity of the compressed text by calculating and comparing the SHA-256 hash against the sha256_full field.
- Only upon confirmed verification, apply the dictionary to expand placeholders.
- Do not alter any portion of the text.

Confirm when you are ready to receive chunks/manifest.json.
```

---

### Stage 2.2: Insertion of chunks/manifest.json
```text
This is chunks/manifest.json.

It defines for each file:
- destination path
- ordered list of chunks (e.g. 0001.txt, 0002.txt, ...)
- sha256_full: expected SHA-256 hash of the concatenated compressed file (prior to placeholder expansion)
- chunk_size and total_len

Instructions:
- Do NOT begin reassembly.
- Do NOT apply any substitution.
- Confirm receipt by stating file paths and the total number of expected chunks for each.

(Paste here the content of chunks/manifest.json)
```

---

### Stage 2.3: Insertion of Mapping Vocabulary
```text
This is the placeholder vocabulary associated with the chunks.

Instructions:
- Register it as an exact vocabulary.
- Do NOT apply substitutions yet.
- Confirm receipt by indicating protocol format and the number of indexed entries.

(Paste here protocol_header.txt + mapping_subset.txt or mapping_subset.json)
```

---

### Stage 2.4: Insertion of Chunk Fragments
```text
Below I send you the progressively numbered fragments.

Instructions:
- Store each block associating it with the file and the specified numeric sequence (e.g. chunk 0001.txt, chunk 0002.txt).
- Do NOT reconstruct yet.
- Confirm receipt specifying the sequence numbers received. If you find gaps in numbering, report it immediately.

(Paste here individual chunks marked by their name, e.g. === CHUNK: src/service.py/0001.txt ===)
```

---

### Stage 2.5: Two-Stage Reassembly and Integrity Verification
*(Command to send only after transmitting all chunks specified in the manifest)*

```text
Proceed with reassembly and reconstruction.

Strictly execute the procedure in the following two consecutive stages:

STAGE 1: CONCATENATION AND INTEGRITY VERIFICATION (sha256_full)
1. For each file, concatenate the blocks in the exact order specified in the chunks array of chunks/manifest.json (0001.txt + 0002.txt + ...).
2. Compute the SHA-256 hash of the compressed text resulting from concatenation.
3. Compare the calculated hash with the expected value present in the sha256_full field of chunks/manifest.json:
   - If it MATCHES: report "STAGE 1 PASSED: sha256_full integrity verified successfully" and proceed to Stage 2.
   - If it DOES NOT MATCH: Strictly HALT the procedure and return: "CRITICAL ERROR: sha256_full discrepancy on reassembled compressed text. Detected possible loss or corruption during copy-pasting of chunks."

STAGE 2: PLACEHOLDER EXPANSION AND DECOMPRESSION
4. On the compressed text verified in Stage 1, expand each placeholder by replacing it with the corresponding text registered in the mapping.
5. Respect longest-first precedence on tokens and do not make any changes to spacing or code.

Return:
- Explicit report of Stage 1 verification (calculated hash vs expected sha256_full).
- Completion status: "FULL RECONSTRUCTION COMPLETED".
- The decoded code ready for analysis.
```

## Technical Notes for the Operator User

1. **Upstream Boundary-Aware Guarantee**:  
   Chunks created by `chompress` never cut placeholder symbols (`一`, `^1`, `«1»`, etc.) in half and always backtrack to the nearest `\n` line delimiter. Each chunk always ends with syntactically intact instructions.
2. **Key Role of `sha256_full`**:  
   Verifying `sha256_full` prior to decoding placeholders allows immediate isolation of any truncations or alterations introduced by the chat interface during copy-pasting, preventing wasted tokens on partial code analysis.
3. **Reference Savings Formulas (Pure ASCII)**:
   ```text
   net_tokens_saved = original_tokens - (compressed_payload_tokens + mapping_tokens + protocol_tokens)
   net_compression_ratio = ((net_tokens_saved) * 100.0) / (original_tokens)
   ```
